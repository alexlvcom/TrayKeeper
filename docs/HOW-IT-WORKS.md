## What Windows stores

Everything lives under one current-user key, which backs
**Settings → Personalization → Taskbar → Other system tray icons**:

```
HKEY_CURRENT_USER\Control Panel\NotifyIconSettings
```

Each subkey is one tray icon. The subkey name is an opaque decimal 64-bit hash
generated by Explorer; Tray Keeper never creates, deletes, or invents one.

| Value | Type | Meaning |
|---|---|---|
| `ExecutablePath` | REG_SZ | Owning executable. **May be prefixed with a KNOWNFOLDERID** — see below. |
| `IsPromoted` | REG_DWORD | `1` = shown on the taskbar, `0` = in the overflow flyout. **Often absent; absent behaves as `0`.** |
| `UID` | REG_DWORD | The `uID` field of the owning `NOTIFYICONDATA`. |
| `IconGuid` | REG_SZ | The `guidItem` of the owning `NOTIFYICONDATA`, for GUID-identified icons. |
| `InitialTooltip` | REG_SZ | Tooltip captured when the icon first appeared. |
| `Publisher` | REG_SZ | Publisher string recorded by Explorer. |
| `IconSnapshot` | REG_BINARY | Cached PNG of the icon. Never read or written by Tray Keeper. |

**Tray Keeper writes exactly one value: `IsPromoted`, and only ever `0 → 1`.**
Nothing else is modified, nothing machine-wide is touched, and no elevation is
requested.

## `ExecutablePath` is not always a path

Entries below a well-known root are stored with a known-folder GUID instead of a
literal path:

```
{6D809377-6AF0-444B-8957-A3773F02200E}\WindowsApps\Claude_1.22209.3.0_x64__pzs8sxrjxfjjc\app\claude.exe
{1AC14E77-02E7-4E5D-B744-2EB1AE5198B7}\Taskmgr.exe
```

| GUID | KNOWNFOLDERID | Resolves to |
|---|---|---|
| `{F38BF404-1D43-42F2-9305-67DE0B28FC23}` | `FOLDERID_Windows` | `C:\Windows` |
| `{1AC14E77-02E7-4E5D-B744-2EB1AE5198B7}` | `FOLDERID_System` | `C:\Windows\System32` |
| `{6D809377-6AF0-444B-8957-A3773F02200E}` | `FOLDERID_ProgramFilesX64` | `C:\Program Files` |
| `{7C5A40EF-A0FB-4BFC-874A-C0F2E0B9FA8E}` | `FOLDERID_ProgramFilesX86` | `C:\Program Files (x86)` |

On the machine this was developed against, **34 of 57 entries** used a prefix. Tray
Keeper expands them with `SHGetKnownFolderPath` before doing anything else; without
that step most entries would yield no file metadata at all.

## Changes apply immediately

Verified on Windows 11 build 26200: Explorer watches this key and applies an
`IsPromoted` change within roughly 1–3 seconds, in both directions, with **no
broadcast and no Explorer restart**.

Tray Keeper therefore does not send `WM_SETTINGCHANGE` and never restarts Explorer.
The results window has an explicit **Restart Explorer** button purely as a manual
escape hatch; it always asks first and is never triggered automatically.

## Duplicate detection

Matching is deliberately biased toward **false negatives**: a still-hidden icon is a
minor annoyance, while surfacing an unrelated application's icon is a visible
defect.

A hidden entry is enabled only if an already-enabled entry passes **every** gate:

1. **Same executable file name** (case-insensitive).
2. **Different executable path.** Identical paths mean two separate icons of one
   process (Outlook registers one for new mail and one for the main window), not an
   update duplicate.
3. **Same icon identity** — equal `UID`, or equal `IconGuid`. One executable can
   legitimately own several icons, each with its own visibility; a setting must never
   be carried across them.
4. **Executable still exists on disk.** Windows keeps an entry per version forever,
   so promoting a deleted version would create an icon that can never appear.

…and then at least one positive signal:

| Signal | Weight |
|---|---|
| Same MSIX package family name (`Name_PublisherId`, version independent) | 100 |
| Same directory after version segments are collapsed | 80 |
| Same product name **and** company | 40 |
| Same file description **and** company | 30 |
| Same tooltip **and** company | 20 |

Version collapsing maps `app-1.5.1095` and `app-1.6.224` both to `app-#`, and
`PhpStorm 2025.1.7` to `phpstorm #`, while leaving non-versions such as `Office16`,
`x64` and `current` alone.

Two rules follow directly from the brief:

- **Company name alone is never sufficient** — it is only ever a co-factor.
- **A generic executable name is never sufficient.** For `update.exe`,
  `helper.exe`, `service.exe`, `electron.exe` and similar, metadata agreement is
  ignored; only package-family or normalized-directory evidence qualifies.
